Technical Report: Oracle Machine Learning (OML) Proof of Concept

Project: Claim Denial Predictive Modeling Environment: RXHDEV / RXHCUSTOM Algorithm: Generalized Linear Model (GLM) Classification

1. Executive Summary

This report outlines the technical workflow and database architecture implemented for the Oracle Machine Learning (OML) Proof of Concept (POC). The goal of this POC is to build, train, and evaluate an in-database binary classification model to predict healthcare claim denials (CLAIMDENIALGLM). By leveraging Oracle's native DBMSDATAMINING package, data preparation, model training, and scoring are executed entirely within the database layer, maximizing performance and eliminating the need for data egress.

2. Data Engineering & Feature Pipeline

The pipeline begins by engineering a unified feature set from the core transaction table RXHCUSTOM.rxcclaim.

Feature Selection & Transformation (rxcclaimfeatures_v)

A source view was created to isolate relevant attributes, normalize strings, handle null values, and map the target class.

  • Target Variable Mapping: The model trains on a binary target column, deniallabel, derived from the ingestion status (icstatus) :
  • 'Y' (Denied) if status is 'IHUB REJECTED'.
  • 'N' (Accepted/Default) if status is 'IHUB ACCEPTED' or any unknown status.
  • Financial Features: Numerical values are scrubbed using NVL transformations to avoid missing values: totalinvoicecharges, totalamountpaid, and balance_due.
  • Demographic & Categorical Features: Text fields are standardized to uppercase to guarantee consistency across categorical dimensions (such as patientsex, patientstate, payertype, and icdversion).
  • Flag Indicators: Complex conditional logic consolidates various database flags into clean, binary numeric inputs (1 or 0) for the algorithm :
  • accident_flag: Combined from auto and miscellaneous accident indicators.
  • otherinsflag: Triggered if secondary policy numbers or secondary benefit plan flags exist.
  • pregnancyflag & errorflag_num: Standardized boolean flags.

Dataset Split & Materialization (claimsmldata)

To preserve consistency across training and testing phases, the view is materialized into a physical table. A random splitting strategy is applied using DBMS_RANDOM.VALUE() to segment the data :

  • Train Set (TRAIN): Approximately 80% of the data.
  • Test Set (TEST): Approximately 20% of the data.

A downstream view, claimsmltrain_v, filters exclusively for the TRAIN partition to supply data to the training algorithm.

4. Evaluation Strategy & Inference

Scoring View (claimsmltestscoresv)

Inference is performed dynamically on the holdout TEST dataset using native OML SQL analytical functions. This step bypasses external prediction runtimes and scores records directly inside database memory.

The inference view generates three core evaluation columns :

  1. pred_label: The hard binary classification prediction (Y or N) using PREDICTION().
  1. probdenied: The calculated probability that the claim will be denied using PREDICTIONPROBABILITY().
  1. prob_accepted: The calculated probability that the claim will be accepted.

Analytics and Validation Metrics

The proof of concept script establishes two direct methods for analyzing model performance on unseen data :

  • Confusion Matrix Analysis: Grouping actual versus predicted labels to calculate True Positives, False Positives, True Negatives, and False Negatives [cite: 14]. SELECT actual label, pred label, COUNT(*) AS n FROM rxh dev.claims ml test scores v GROUP BY actual label, pred label ORDER BY actual label, pred _ label;
  • Overall Accuracy: Formulated via SQL to establish the baseline correctness rati SELECT ROUND( SUM(CASE WHEN actual label = pred label THEN 1 ELSE 0 END) / COUNT(*), 4 ) AS accuracy FROM rxh dev.claims ml test scores _ v;

5. Next Steps & Recommendations

  1. Hyperparameter Tuning: Evaluate hyperparameter configurations within GLMCLAIMSETTINGS (e.g., explicitly enforcing BINOMIAL family or LOGIT link functions) to contrast baseline performance.
  1. Feature Expansion: Re-integrate commented date parameters (invoicecompletedate, icstatusdate) using proper time-delta transformations to calculate duration metrics.
  1. Alternative Classifiers: Utilize the established framework to construct alternative algorithms (such as Random Forest or Naive Bayes) by swapping settings parameters to perform a model comparison audit.
