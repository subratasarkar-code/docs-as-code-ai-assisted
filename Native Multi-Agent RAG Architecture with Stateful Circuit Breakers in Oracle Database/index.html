📄 TECHNICAL REPORT

Title: Native Multi-Agent RAG Architecture with Stateful Circuit Breakers in Oracle Database

Author: Subrata Sarkar

Date: March 2026

1. Executive Summary

This technical report details the successful implementation of a database-native, asynchronous Multi-Agent Retrieval-Augmented Generation (RAG) system. While traditional AI agent frameworks heavily rely on external Python compute environments (e.g., LangGraph, Databricks), this Proof of Concept (POC) demonstrates that advanced agentic workflows—complete with complex state management, quality control loops, and API fail-safes—can be executed entirely inside an Oracle Database instance.

By leveraging native database capabilities, the system achieves lower latency by eliminating network data movement, utilizes highly robust security protocols, and maintains transaction-safe conversation states.

2. Problem Statement

Modern enterprise RAG systems typically separate the data layer (the database) from the application execution layer (Python/LangChain). This introduces several critical overheads:

  1. Infrastructure Bloat: Maintaining separate Python servers or Databricks clusters purely for agentic state routing.
  1. Data Gravity Challenges: Shuttling massive sets of document chunks across the wire to external APIs introduces latency and security risks.
  1. State Volatility: Managing crash-resilient short-term memory across microservices is complex and prone to data loss.

3. System Architecture & Methodology

The solution shifts the orchestration paradigm by using the database as both the source of truth and the execution brain .

3.1 The "Blackboard" Design Pattern

Figure 1: Native Multi-Agent Architecture with Stateful Circuit Breakers & Blackboard Pattern Click image to enlarge

Instead of hardcoding a linear flow of execution (Agent A calling Agent B), a decoupled blackboard design was utilized via a control table named AGENT _ BLACKBOARD .

  • Requests are logged as a centralized row.
  • Agents act as independent background workers that read the state of the blackboard, process their task, and flip the status for the next agent to consume.

3.2 Implemented Agents

Three specialized database agents were constructed to simulate a team of human collaborators:

  1. The Search Agent: Watches for incoming initialized rows. It performs the vector query against the document _ chunks table and loads relevant domain context onto the blackboard.
  1. The Synthesizer Agent: Observes completed searches. It calls external LLMs to answer the prompt based purely on the loaded search data.
  1. The Critic Agent: Evaluates the quality of the Synthesizer's output. If it detects halucinations or insufficient details, it rejects the answer, inserts feedback on the blackboard, and forces the Synthesizer to regenerate the response.

4. Key Advanced Features

The POC successfully proved out two massive enterprise scaling mechanics:

4.1 Stateful Circuit Breaker

To prevent runaway compute costs or API timeouts from locking up database sessions, a custom circuit breaker package was written.

  • If external LLM integrations fail consecutively beyond a set threshold (e.g., 3 failures), the circuit trips to OPEN .
  • Subsequent calls are automatically throttled and rejected at the DB level until a cooldown timeout expires, moving it back to HALF-OPEN or CLOSED .

4.2 Asynchronous True Autonomy via DBMS_SCHEDULER

To mirror external microservices, the agents were decoupled from continuous procedural execution. Standalone procedures were written and mapped to polling jobs running on a short interval via DBMS _ SCHEDULER . Using native FOR UPDATE SKIP LOCKED logic, multiple parallel jobs can scale horizontally to handle heavy message queues without causing deadlocks.

5. Successful Execution Evidence & Results

The final verification test established full operational integrity.

A query regarding JSON features was injected into the blackboard.

  • The system executed the vector search correctly, processing a CLOB text pool and identifying relevant vectors.
  • The synthesizer drafted an outline highlighting flexibility and agility in JSON.
  • The critic approved the output without fault on that cycle, officially resolving the row state to CRITIC _ APPROVED without leaving any error messages in the execution logs.

6. Recommendations & Next Steps

Based on the high performance of this POC, the following implementations are recommended for production environments:

  • APEX 24.2 Front-End Integration: Leverage a dynamic timer or polling action to reflect the blackboard status in real-time to end-users without page refreshes.
  • Vector Model Transition: Move to complete, in-database model storage via Oracle 23ai/26ai's onnx local model hosting to remove the internet API factor entirely.

❓ Frequently Asked Questions & Practical Scenarios

Operational clarifications, design trade-offs, and architecture decisions related to this technical document.

The AGENT_BLACKBOARD table acts as the shared state store. Requests enter with an initialized status. Autonomous background agents continuously poll for actionable rows matching their specific agent stage, execute their logic, and advance the state column to trigger downstream agents.

Each agent runs as an independent DBMS_SCHEDULER job executing procedures with SELECT ... FOR UPDATE SKIP LOCKED. This enables multiple concurrent worker threads to claim and process separate blackboard rows simultaneously without lock contention.

The Critic Agent evaluates the Synthesizer Agent's output against the source document chunks retrieved by the Search Agent. If it detects hallucinations, missing context, or low confidence, it rejects the draft, writes feedback onto the blackboard, and resets the status for regeneration.

If external API calls fail consecutively beyond a configured threshold (e.g. 3 failures), the circuit breaker transitions from CLOSED to OPEN, immediately failing subsequent requests at the database layer. After a cooldown window, it shifts to HALF-OPEN to safely test external connectivity.
