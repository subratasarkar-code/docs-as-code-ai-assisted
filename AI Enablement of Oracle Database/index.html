Objective

The objective of this Proof of Concept (POC) was to evaluate how AI capabilities available in Oracle Database 26ai can be integrated with Oracle APEX 24.2 to enable intelligent data interaction within enterprise applications.

The POC demonstrates how unstructured document data can be ingested, processed, and queried using vector embeddings and Retrieval Augmented Generation (RAG).

This approach allows business users to interact with enterprise knowledge using natural language queries while leveraging Oracle’s in-database AI capabilities.

Background

Traditional enterprise applications require users to interact with structured queries or predefined reports. With the introduction of AI-enabled features in Oracle Database 26ai, it becomes possible to allow users to interact with data using natural language prompts and intelligent assistance.

Oracle APEX 24.2 provides a rapid development platform that can expose these AI capabilities through web applications without requiring extensive application development.

This POC explores the integration between Oracle Database AI services and Oracle APEX for building intelligent enterprise applications.

Technology Stack

Unstructured Document AI Workflow

Figure 3: Unstructured Document Ingestion & Chunk Vectorization Workflow Click image to enlarge
  1. Users upload documents through Oracle APEX.
  1. Documents are stored in the database as CLOB data. The text is chunked into segments of approximately 100 words.
  1. Embeddings are generated for each chunk using the OpenAI API and stored as vectors in Oracle Database 26ai.
  1. When a user submits a query, a vector similarity search retrieves relevant chunks which are combined with the prompt to generate a response using Retrieval Augmented Generation.

RAG Implementation Flow for Document Upload and Query Processing

Figure 4: RAG Implementation Flow for Document Upload and Query Processing Click image to enlarge

Stage 1 – Document Ingestion

  1. User uploads document through Oracle APEX UI
  1. Document stored in database as CLOB
  1. Text extracted and cleaned
  1. Text segmented into ~100 word chunks
  1. Embeddings generated via OpenAI API
  1. Embeddings stored in vector table

Stage 2 – Query Processing

  1. User submits natural language query
  1. Query converted into vector embedding
  1. Vector similarity search retrieves top-N relevant chunks

Stage 3 – Response Generation

  1. Retrieved chunks combined with user query
  1. Prompt constructed for LLM
  1. LLM generates contextual response
  1. Response displayed in APEX UI

❓ Frequently Asked Questions & Practical Scenarios

Operational clarifications, design trade-offs, and architecture decisions related to this technical document.

Co-locating vector embeddings with relational enterprise data eliminates the security risks, network latency, and operational complexity of external data egress. It guarantees ACID transaction safety and allows SQL queries to join vector similarity results directly with live business tables.

A 100-word chunk size strikes the ideal balance between semantic specificity and context retention. It prevents dilution of embedding vectors while remaining compact enough to assemble highly focused prompts for the LLM without exceeding token context limits.

APEX 24.2 utilizes native Web Credentials and APEX_WEB_SERVICE PL/SQL APIs to issue secure REST calls directly to the OpenAI endpoints for embedding generation and completions.

Financial analytics dashboards, fraud detection systems, customer insight platforms, AI-driven reporting tools, and internal enterprise knowledge assistants querying unstructured documentation.
