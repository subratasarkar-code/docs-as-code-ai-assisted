Oracle AWR Interpretation Guide

A Top-Down Diagnostic Approach for Database Performance Tuning

Interpretation of an Oracle Automatic Workload Repository (AWR) report requires a top-down methodology. Start at the system overview level, identify the primary bottleneck (CPU vs. Wait Events), and follow that thread directly to the responsible SQL IDs or system components.

1. Context & Overhead (Header & Load Profile)

Before analyzing specific wait events, verify snapshot context and overall database load.

  • Snapshot Window: The ideal snapshot window is 30 to 60 minutes covering the target problem period. Avoid multi-hour snapshots as they average out performance spikes and obscure short-duration bottlenecks.

Average Active Sessions (AAS): Calculate AAS to quantify database concurrency relative to capacity:

Average Active Sessions (AAS) = DB Time / Elapsed Time

  • AAS < CPU Cores: The system had spare processing capacity. Bottlenecks are likely localized to specific sessions or locking scenarios.
  • AAS > CPU Cores: The database was resource-saturated during the snapshot window.

-

Key Load Profile Metrics:

  • Hard Parses / sec: Values consistently exceeding 100/sec indicate un-bound SQL statements causing CPU overhead and library cache latch contention.
  • Logical vs. Physical Reads: Extremely high logical reads relative to physical reads indicate queries thrashing the buffer cache and consuming excess CPU.

3. SQL Statistics Section

Map the identified wait event or resource bottleneck directly to offending SQL statements using these subsections:

  • SQL ordered by Elapsed Time: Pinpoint statements consuming the highest overall execution time. Compare total Executions vs. Elapsed Time per Exec (s) .
  • SQL ordered by CPU Time: Identify statements consuming high CPU resources (algorithmic complexity, memory sorts, or high buffer gets).
  • SQL ordered by Gets (Buffer Gets): Find queries driving excessive buffer cache churn.

-

  • SQL ordered by Reads (Physical Reads): Locate queries bypassing cache and driving storage I/O.

-

  • SQL ordered by Parse Calls: Identify statements incurring excessive soft or hard parse overhead.

-

4. Memory & I/O Advisories

If SQL tuning does not resolve performance issues, evaluate database memory and storage subsystem health:

  • Buffer Pool Advisory: Evaluates expected physical read reductions if dbcachesize is increased.

-

  • PGA Aggregate Target Advisory: Shows whether increasing pgaaggregatetarget will keep large sorts and hash joins in memory rather than spilling to TEMP .
  • Tablespace / File I/O Statistics: Check Avg Read(ms) per data file. Latencies consistently above 10–15 ms indicate storage subsystem bottlenecks.

5. Diagnostic Workflow Summary

  • 1Calculate AAS:Determine overall load relative to available CPU cores using DB Time / Elapsed Time .
  • 2Analyze Top Timed Events:Categorize primary system wait profile as eitherI/O / Wait BoundorCPU / Parse Bound .
  • 3Map to SQL Statistics:Match wait categories to corresponding SQL sections (Reads, CPU, Buffer Gets, or Parse Calls) to extract top target SQL_ID s .
  • 4Fetch Historical Execution Plan:Retrieve execution details for offending queries directly from AWR memory repository.

To pull the exact execution plan used during the AWR window for a target SQL ID:

sql 
SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_AWR('your_sql_id_here'));

💡 Key Takeaway

Always correlate system-level wait events with specific SQL IDs before making database parameter or infrastructure changes. Tuning the top 2-3 SQL statements identified in AWR frequently resolves 80%+ of total system contention.

❓ Frequently Asked Questions & Practical Scenarios

Operational clarifications, design trade-offs, and architecture decisions related to this technical document.

AAS = DB Time / Elapsed Time. If AAS is less than the number of available CPU cores on the host, the database is operating within capacity. If AAS significantly exceeds CPU cores, the system is bottlenecked and sessions are queuing.

'db file sequential read' represents single-block I/O, typically caused by index lookups. 'db file scattered read' represents multi-block I/O, typically caused by full table scans or fast full index scans.

High log file sync indicates commit latency. Resolve by eliminating commits inside loops (batch commits), optimizing redo log storage I/O latency, or increasing redo log file size to prevent excessive log switches.

Execute SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_AWR('your_sql_id_here')); directly against the database to view the historical plan stored in the AWR repository.
